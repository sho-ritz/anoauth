# Decisions

| # | Topic | Decision |
|---|---|---|
| 1 | Boundary with anoDB (2026-11-15) | anoDB handles membership by public key only (anoDB DECISIONS 27). anoAuth decides *who* may join and calls `addMember` on an owner / admin device. Joiners hand over `db.deviceDelegations()` |
| 2 | Members (Q1) | Members are anoDB pubkeys. A space can also hold **reservations** for external identities (e.g. "alice@company.com as writer"); the first valid proof from that identity turns into membership of the proving pubkey |
| 3 | Who admits (Q2) | Only **owner / admin devices** verify proofs and admit, automatically and without a click. Other devices only check that an admin added the member, so membership is deterministic and writers cannot bypass the rules. Admission waits until an admin device is online |
| 4 | Entry point (Q3) | The **invite link** carries where to send the request and which proof types are accepted. Rule contents (e.g. email lists) stay encrypted in the space. Approval-only links behave like anoDB's former one-time links |
| 5 | Link lifetime (Q4) | Proof-based links are **reusable**, expire after 30 days by default (or never), and can be revoked. Approval-only links are single-use |
| 6 | Token age (Q5) | An OIDC ID token is accepted if **issued within 7 days** (configurable), ignoring its 1-hour `exp`. Its `nonce` must bind the applicant's pubkey, so a stolen token is useless for another key |
| 7 | Losing eligibility (Q6) | Members admitted by an external proof **re-prove every 90 days** (configurable, can be off). Without a fresh proof an admin device removes them and rotates the key. NIP-05 can be rechecked by the admin; OIDC is refreshed by the member's app, prompting only when needed. npub / link / approval members are exempt |
| 8 | First release (Q7) | Proof types: invite link, npub, manual approval, **signed certificate from a trusted issuer key** (the entry point for a future anoAuth issuer or a company system; verifiable offline), and **OIDC** (separate package). NIP-05 later. All are plugins of the same shape |
| 9 | Where rules are written (Q8) | Rules are **data**, signed and stored encrypted, so every admin applies the same rules and an admin screen can change them at runtime: `setRules(space, [{ proof, emailDomain / email / claim…, role }])`. An app hook (`check(req)`) covers what data cannot express |
| 10 | Where anoAuth state lives (Q9) | A separate **admin space** per space (members: the space's owner and admins, kept in sync by anoAuth) holds rules, reservations, issued links and admission records. Regular members cannot read or change them. No new anoDB feature is needed |
| 11 | When no admin is online (Q10) | By default the request waits and is processed as soon as an admin opens the app (the applicant sees that it is waiting). For instant admission, an always-on **gatekeeper** (`npx anoauth gatekeeper`, a Node admin device) is officially supported. It is an admin, so it can read the space |
| 12 | Certificate format (Q11) | A **signed Nostr event** (secp256k1 / Schnorr, as in anoDB): the issuer is an npub, the event names the subject pubkey, its attributes (email, department…) and an expiry. Verifiable offline, no extra dependencies |
| 13 | Packages (Q12) | `@anoauth/core` (rules, links, requests, admission through a given anoDB, certificate verification: `createAnoAuth(db)`), `@anoauth/oidc` (Google / Microsoft / company SSO sign-in and verification), `@anoauth/react` (invite link, join screen, rule editor), `@anoauth/cli` (gatekeeper) |
| 14 | Who edits rules (Q13) | Owner and admins edit rules and reservations and issue / revoke links. Only the **owner** can create a rule that grants `admin` (matching anoDB, where admins cannot make admins); such requests are admitted only by an owner device |
| 15 | Admission records (Q14) | Keep only the essentials in the admin space: pubkey, proof type, issuer, subject (e.g. email), admitting admin, time. Raw tokens are not stored |
| 16 | Same identity, another key (Q15) | **One external identity = one pubkey per space.** A second key is not admitted automatically; the applicant is told to add the new device from an existing one. If every device is lost, an admin confirms and replaces the old key with the new one. One person cannot multiply seats |
| 17 | OIDC audience | A rule pins the issuer **and the app's client id (`aud`)**; tokens issued to another app are rejected. The browser gets the ID token directly from the provider (no server); the nonce is `sha256(applicant pubkey + link secret)` |
| 18 | Implementation notes (v0.1, 2026-11-15) | Requests travel as kind 7383 envelopes, NIP-44 encrypted with a key derived from the link secret and signed by a throwaway key, routed by an `n` tag only secret holders can compute. **No proof of key possession is needed** from the applicant: keys are only delivered to the devices named by delegations signed by that identity, and the invitation must still be accepted there, so submitting someone else's delegations gains nothing. Renewals use a per-space channel secret stored in the guarded space (members can read it; only members' renewals are processed). anoDB's `addMember` uses already-known devices when `devices` is omitted, so the owner can add admins to the admin space |
| 19 | Packages and OIDC (v0.1, 2026-11-15) | npm workspace: `packages/core`, `packages/oidc`, `packages/react`. **OIDC**: the browser gets the ID token straight from the provider with the implicit `id_token` flow in a popup (no server, no client secret); `nonce = proofNonce(applicant pubkey, link secret)` (`auth.nonceFor(link)`); admins verify RS256 / ES256 with the provider's JWKS via discovery, pin `iss` and `aud`, accept tokens issued within 7 days, and use the verified email (or `sub:`) as the subject. The popup returns to the app, which must call `handleOidcRedirect()` before opening the database. **React**: `<InviteLinks>`, `<JoinRequests>`, `<RulesEditor>`, `<JoinWithLink proofs={[oidcProofSource(…)]}>`; `isAdminSpace()` hides admin spaces from room lists. Sending a request waits for two relay connections and retries, since some relays refuse unknown pubkeys |
| 20 | Gatekeeper (v0.1, 2026-11-15) | `@anoauth/cli gatekeeper --app … --trust <owner npub>`: its own identity (keys in a mode-600 file, group keys sealed with a key derived from the device key), publishes a key package, accepts invitations **only from trusted owners**, and runs anoAuth like any admin device. The owner adds it with `addMember(space, npub, 'admin')`; the owner's device must be online once to add it to the admin space. It can read the spaces it guards |
